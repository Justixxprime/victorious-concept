## 1. Payments (Paystack) — 🔴 CRITICAL

**What exists:** `src/pages/Checkout.jsx` builds a Paystack config client-side (`amount: totalPrice * 100`, using the cart's client-computed `totalPrice`), calls `usePaystackPayment`, and on `onSuccess` immediately calls `placeOrder(reference.reference, 'card')`, which inserts the order into Supabase directly from the browser using the anon key.

**Why it's insufficient:** There is no webhook handler, no serverless function, and no Supabase Edge Function anywhere in the repo (`api/` only contains `send-order-confirmation.js`, for email). That means:
- Nothing verifies with Paystack's servers that the transaction actually succeeded, for the amount charged, in the right currency, before the order is recorded as paid.
- The **amount charged is whatever the browser sent** — a modified client could send any `amount`, and Paystack would charge that, while a modified `totalPrice` variable could also make the order record show a different total than what was paid.
- The success callback (`onSuccess`) firing is being treated as proof of payment. Paystack popup callbacks can be spoofed or the network call can be short-circuited by anyone with dev tools.
- There's no idempotency check, so if `onSuccess` fires twice (double click, popup edge case), nothing stops a duplicate order/insert.

**Why it matters:** This is the single highest-risk item in the whole codebase — it's the difference between "a demo checkout" and "a payment system real customers can trust with money." As-is, a technically inclined bad actor could pay for a cheap item and manipulate the client to record a large order as paid, or vice versa.

**What should be done:**
1. Move order creation to *before* payment: create the order as `pending_payment` with a server-calculated total (see §3), then initialize Paystack with a `reference` tied to that order.
2. Add a Paystack webhook endpoint (Vercel serverless function, e.g. `/api/paystack-webhook.js`) that verifies the `x-paystack-signature` header against `PAYSTACK_SECRET_KEY` (never exposed to the client), then calls Paystack's "verify transaction" API to confirm amount, currency, and reference before marking the order paid.
3. Only the webhook (running with a Supabase service-role key, server-side only) should ever set `payment_status = 'paid'`.
4. Make the webhook idempotent (check `payment_reference` uniqueness before applying).

**Files affected:** `src/pages/Checkout.jsx` (stop writing `paid` status client-side), new `api/paystack-webhook.js`, `api/create-order.js` (or similar) for authoritative order creation.
**Database changes:** `orders` needs a `payment_status` column (see §4) if it doesn't already have one server-trusted.
**Backend changes:** New serverless webhook + verification endpoint; `PAYSTACK_SECRET_KEY` added as a Vercel env var (server-only, never `VITE_`-prefixed).
**Frontend changes:** Checkout no longer writes the paid order directly; it creates a pending order, redirects to Paystack, and polls/reads the order status afterward.

## 2. Admin Authorization — 🔴 CRITICAL

**What exists:** `src/hooks/useIsAdmin.js` is a hardcoded array:
```js
const ADMIN_EMAILS = ['victoriaobioma31@yahoo.com', 'justixxchiobi@gmail.com']
```
`Admin.jsx` and the admin-only branch of `Account.jsx` both gate their UI on `useIsAdmin()`.

**Why it's insufficient:** This is a **frontend-only** check. It correctly hides the admin UI from the wrong people, but it does nothing to stop a logged-in customer from calling the same Supabase queries the admin panel calls (product insert/update/delete, order status change, coupon creation, etc.) directly via the browser console, using their own valid session and the public anon key — *if* the underlying Supabase Row Level Security policies allow it.

**Why it matters:** Whether this is actually exploitable right now depends entirely on the RLS policies configured in the Supabase dashboard, which aren't in this repo and I can't see. This is exactly the trap the brief warns about: `ADMIN_EMAILS` controlling *visibility* is fine; if it's also the *only* thing standing between a customer and writing to `products`/`orders`/`coupons`, that's a critical hole.

**What should be done (needs verification, not guessing):**
1. **[HUMAN INPUT REQUIRED / dashboard check]** — Open Supabase → Authentication → Policies for `products`, `orders`, `coupons`, `categories`, `collections`, `site_settings`. Confirm INSERT/UPDATE/DELETE are restricted to admins at the database level, not just "authenticated". A safe pattern: an `admin_users` table (or a `role` column on `profiles`) checked inside the RLS policy itself, e.g. `USING (auth.uid() IN (SELECT user_id FROM admin_users))`.
2. If policies currently just check `auth.role() = 'authenticated'`, **any signed-up customer can currently write to these tables** — that needs fixing immediately, independent of anything else in this audit.
3. Keep `useIsAdmin.js` for UI visibility, but stop treating it as security.

**Files affected:** `src/hooks/useIsAdmin.js` (fine to keep for UI), Supabase dashboard policies (out of repo).
**Database changes:** Possibly a `role` column / `admin_users` table + rewritten RLS policies.

## 3. Client-Trusted Pricing — 🔴 CRITICAL

**What exists:** `Checkout.jsx` sends `totalPrice` (computed client-side in `CartContext.jsx` from cart items + coupon discount) straight to both Paystack and the `orders` insert. Coupon validation (`src/context/CartContext.jsx`) fetches the coupon row and applies `subtotal * (coupon.percent_off / 100)` **in the browser**.

**Why it's insufficient:** Nothing on a server recomputes the price from authoritative product data before charging or recording it. A modified `totalPrice`, a modified `coupon.percent_off` (if RLS allows public read+no server recheck), or a locally-edited cart item price would all be trusted as-is.

**Why it matters:** This is the core of "never trust the client for price" from the brief, and right now the client is the only source of truth for what's charged.

**What should be done:** Same fix as §1 — introduce a server-side order-creation step that re-fetches each product/variant's real price and stock from the database, recomputes subtotal/discount/total, and *that* number (not the one the browser sent) is what gets sent to Paystack and stored.

**Files affected:** `src/pages/Checkout.jsx`, `src/context/CartContext.jsx` (coupon fetch can stay for UI preview, just not as final authority), new server endpoint.

## 4. Order Data Model — 🟠 IMPORTANT

**What exists:** From `Checkout.jsx`'s insert call, the `orders` table stores: `user_id, order_number, items (jsonb), total, customer_name, customer_phone, customer_address, payment_reference, payment_method`. No `payment_status` or `order_status` field is set on insert.

**Why it's insufficient:** Per the brief's model, payment status (unpaid/pending/paid/failed) and order status (pending_payment/processing/shipped/delivered...) should be separate, explicit, trackable fields — not inferred from `payment_method` alone. Right now a bank-transfer order and a "paid" card order look the same in the table except for `payment_method`, which means admin has no query-able way to see "which orders are actually paid yet."
**[UNVERIFIED — needs dashboard check]**: it's possible these columns already exist in the Supabase table with defaults even though the insert doesn't set them; I can only see what the frontend writes, not the full table schema. Worth confirming directly in Supabase's table editor.

**Why it matters:** Without a real status field, the admin can't safely tell paid orders from unpaid ones, which is core to daily operations (and to fixing §1).

**What should be done:** Add/confirm `payment_status` (`unpaid | pending | paid | failed | refunded`) and `order_status` (`pending_payment | processing | shipped | delivered | cancelled`) columns; set them explicitly on every insert/update path (card → `unpaid` until webhook confirms `paid`; bank transfer → `pending` until admin manually verifies; WhatsApp → `pending`).

**Files affected:** `src/pages/Checkout.jsx`, `src/pages/Admin.jsx` (Orders tab), Supabase `orders` table.

## 5. Inventory / Stock Protection — ⚫ MISSING

**What exists:** `products` has a `stock` field (used for display/status per the site's feature set), but I found **no code anywhere in the order-placement path that decrements stock** when an order is placed (checked `Checkout.jsx`, `CartContext.jsx` — no stock mutation).

**Why it's insufficient:** Two customers can buy the last unit of a product at the same time and both "succeed" — there's nothing preventing overselling.

**Why it matters:** For a real store, this is a direct path to broken promises to customers (selling something that isn't actually available).

**What should be done:** When an order moves to `paid`/confirmed, atomically decrement stock (a Postgres function/RPC that does `stock = stock - qty WHERE stock >= qty`, failing the order item if insufficient — not a plain read-then-write from the client, which is a race condition). This naturally belongs in the same server-side order-confirmation step as §1 and §3.

**Files affected:** New Supabase RPC/function, called from the payment-verification server code, not the client.

## 6. Guest Checkout Not Persisted — 🟠 IMPORTANT

**What exists:** In `Checkout.jsx`, `placeOrder()` only calls `supabase.from('orders').insert(...)` **inside `if (user)`**. If someone checks out without an account, no order row is ever created — the only record is whatever gets sent via WhatsApp text (and even that's just a pre-filled message, not guaranteed sent).

**Why it's insufficient:** Any guest who pays by card and closes the tab before/without an account has no order in the database at all — no receipt lookup, no admin visibility, no way to fulfill it except manually digging through Paystack's dashboard.

**Why it matters:** This is a real money-losing/trust-losing gap, and it directly contradicts the site having a `/track-order` guest-lookup feature (per your project notes) — that feature can't find orders that were never saved.

**What should be done:** Persist every order regardless of login state (store a nullable `user_id`, always store `customer_phone`/`order_number` for guest lookup). This becomes straightforward once order creation happens server-side (§1) rather than gated on `user` existing.

**Files affected:** `src/pages/Checkout.jsx`.

## 7. Secrets & Environment Variables — 🟡 NEEDS IMPROVEMENT (not critical, but should be fixed)

**What exists:** `.env` is **committed to git history** (`git log -- .env` shows multiple commits touching it, going back to Aug 21). Its current tracked content is:
```
VITE_SUPABASE_URL=...
VITE_SUPABASE_ANON_KEY=...
VITE_PAYSTACK_PUBLIC_KEY=...
```
`.gitignore` does list `.env`, but it was apparently added to git *before* that ignore rule took effect (or added with `git add -f`), so it's still tracked.

**Why it's insufficient:** The good news: everything currently in `.env` is `VITE_`-prefixed, meaning it's already meant to be public (Supabase anon key and Paystack *public* key are designed to be exposed in a browser bundle — this is normal and not a leak by itself). The actual problem is process hygiene: an untracked `.env` file is where secret, non-public keys (Paystack secret key, a future Supabase service-role key, `RESEND_API_KEY`) would eventually get added by habit, and if that ever happens while `.env` is still tracked, a real secret would get pushed to GitHub.

**Why it matters:** Low risk today, high risk the day someone adds a secret key to that same file without thinking about it.

**What should be done:**
1. `git rm --cached .env` and commit — stop tracking it going forward (existing history will still contain the old public-key values, which is acceptable since they're public-by-design, but not worth rewriting history over).
2. Create a proper `.env.example` with placeholder values (currently missing entirely from the repo) so the pattern is documented.
3. Confirm `RESEND_API_KEY` (used in `api/send-order-confirmation.js`) is set only as a Vercel dashboard environment variable, never in a file — this already appears to be the case, since it's not in the tracked `.env`.

**Files affected:** `.env` (untrack), new `.env.example`.

## 8. Coupon Validation — 🟡 NEEDS IMPROVEMENT

**What exists:** `CartContext.jsx` fetches a coupon by code from Supabase and computes the discount client-side (`subtotal * percent_off / 100`); `coupons` table (per your project notes) has `code, percent_off, active`.

**Why it's insufficient:** No server-side re-validation before charging (ties back to §3), and the schema (as known) has no expiry date, usage limit, per-customer limit, or minimum-order checks — so the coupon engine is simpler than the brief's spec, and even the `percent_off`/`active` check it does have isn't re-verified at the point of payment.

**Why it matters:** Coupon abuse (reusing an expired or one-time code) is a realistic risk once the store has real traffic.

**What should be done:** Short-term: fine as-is for a small store with codes Victoria hands out herself. Before scaling: add `expires_at`, `max_uses`, `used_count` columns, and validate all of it server-side during order confirmation, not just client-side.

**Files affected:** `src/context/CartContext.jsx`, `coupons` table, new server-side order-creation code.
